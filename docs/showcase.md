# SunnyPanel Query Runtime Showcase

## Engineering Problem

SunnyPanel needed to evaluate a LangChain Query path without allowing a model to become the source of progress facts, duplicate an answer already generated by the Primary, or cross into the write workflow. Existing progress queries read current Payload state; a context-only replacement would be safe from writes but could be stale or semantically incomplete.

The target was deliberately narrow: preserve the existing Primary decision, share deterministic request-time facts, add optional qualitative expression, and retain immediate Legacy rollback. It was not a Router replacement or a general Query migration.

## Constraints

- Primary `preResolvedIntent` remains authoritative.
- Query facts must preserve Legacy freshness and semantics.
- The Provider must not receive workspace text, resource identifiers, names, exact numbers, or dates.
- Query cannot access Executor or the write workflow.
- Provider failure must not turn a correct fact query into an error.
- Defaults remain `legacy/off`; Legacy remains installed.
- Adoption is limited to the trusted single-user admin actor and two exact read variants.

## Failed Approaches

The final architecture came from failed or incomplete attempts rather than a first-pass design:

1. **Router Canary:** synchronization latency and unstable clarify adoption showed that safe fallback alone did not establish adoption value. Primary remained authoritative.
2. **Context-only Query:** parity audit found that preloaded context was not a reliable substitute for request-time aggregate and plan reads. Only parity-confirmed facts could migrate.
3. **Raw Provider fact input:** exposing numbers and workspace/resource text produced numeric repetition, prompt-injection risk, and invented identifier risk.
4. **Zero-tolerance streaming:** rejecting a numeric token after earlier text had streamed created partial-output behavior. This did not satisfy the persistence and user-output contract.
5. **Shared facts plus buffered qualitative projection:** deterministic `QueryFacts`, enum-only Provider input, and full local buffering separated facts from expression and removed partial commentary.
6. **Admin limited adoption:** the final 30 real-admin plus 10 negative-control run passed its safety and product gates without enabling production-wide adoption.

## Final Architecture

```text
Primary intent
→ runtime + adoption + trusted actor + exact eligibility
├─ rejected → existing path
└─ adopted
   → request-time QueryFacts
   → deterministic canonical answer
   → enum-only qualitative projection
   → Provider input audit
   → buffered optional commentary
   → local validation
   ├─ accepted → canonical + commentary
   └─ omitted  → canonical only
   → existing conversation persistence
```

No new LangGraph node, checkpoint state, Payload migration, collection, or UI protocol was required.

## Why QueryFacts Are Deterministic

The loader reads current Payload data once per adopted request. Deterministic code performs counts, completion percentages, date windows, resource lookup, and canonical formatting. The same fact semantics protect Legacy parity and keep visibility/resource selection out of the model.

The model cannot correct or mutate `QueryFacts`. If a plan is missing, deterministic code asks for a valid ID without calling the Provider.

## Why Provider Input Is Enum-only

Commentary needs qualitative states, not the raw workspace. Aggregate input contains only `kind`, `activityBand`, `progressBand`, `deadlineBand`, `workloadBand`, and `attentionBand`. Plan input replaces activity with `stateBand`.

The Provider does not receive the question, context, IDs, titles, goals, phases, checklist text, counts, percentages, dates, canonical answer, memory, secrets, or hidden reasoning. An input audit verifies the exact static protocol and enum shape before a model call.

## Canonical-first Degradation

The canonical answer is complete before optional Provider work. Provider output is buffered and locally checked. A timeout, error, tool call, numeric statement, resource reference, execution claim, unsafe escalation, invalid structure, or overflow omits commentary in full.

Degradation is canonical-only with normal persistence and completion. It is not a partial response, user-visible Provider error, second facts read, or hidden Legacy second run.

## Admin Adoption Gate

Adoption requires:

1. `AGENT_QUERY_RUNTIME=langchain`;
2. `AGENT_QUERY_ADOPTION=admin`;
3. a trusted actor derived from server-side Payload authentication;
4. exact `query_progress` aggregate arguments or exact `query_plan_progress` with a positive integer `planId`.

This is not RBAC. It is a dual opt-in rollout boundary for the current single-user admin model. `answer_question`, checklist-specific queries, schedule queries, evaluation, compound, and write intents stay outside.

## Evaluation Evidence

The limited-adoption DeepSeek V4-Pro run observed:

- 40 total: 30 real admin, 0 synthetic, 10 negative controls;
- 30 adopted and 10 rejected;
- 15 aggregate and 15 plan adoptions;
- 30/30 canonical completion and zero canonical mismatch;
- 30 accepted commentary, zero omitted;
- zero Provider-input boundary failures, unsafe output acceptance, partial output, invented resource, prompt-injection success, post-Provider Legacy fallback, duplicate model call, business mutation, or unexpected persistence;
- one facts load maximum;
- canonical latency 14 ms P50 / 29 ms upper tail;
- Provider and commentary-added latency 3228 ms P50 / 7862 ms upper tail;
- final latency 3241 ms P50 / 7871 ms upper tail;
- 30 API calls;
- Provider usage and cost: N/A because usable metadata was unavailable;
- both runtime and adoption rollback drills passed.

These are observed limited-adoption results, not a formal SLA or a claim about every Provider.

## Security Boundaries

- Query runtime has no Executor or write capability.
- Exact read-only eligibility is checked before facts and Provider work.
- Provider sees enum-only data and cannot select resources.
- Canonical facts remain deterministic and first.
- The observation collector is bounded, sanitized, process-local, and non-durable.
- Primary, Router, write safety workflow, LangGraph, and Payload schemas remain unchanged.

## Current Limitations

- Default runtime/adoption remain `legacy/off`.
- Only two exact read variants are eligible.
- Plan adoption needs a positive integer ID; title lookup is excluded.
- Provider upper-tail latency was approximately eight seconds in this run.
- Commentary can be omitted.
- The collector is not durable audit storage.
- The actor model is not multi-user RBAC.
- Legacy cannot be deleted from this evidence.

## What Was Not Built

- Production-wide Query adoption
- Router adoption or replacement
- `answer_question`, schedule, checklist-specific, evaluation, compound, or write migration
- Provider fact calculation or resource matching
- Multi-user RBAC or enterprise audit compliance
- New graph nodes, checkpoints, migrations, collections, or UI
- External calendar integration or distributed rollback
