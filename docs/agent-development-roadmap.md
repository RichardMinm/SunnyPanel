# SunnyPanel Agent 开发路线图：从个人效率助手到真正的 AI 个人助手

## 文档概述

本文档基于对 SunnyPanel 当前 Agent 系统与 Claude Code / 理想个人助手之间的差距分析，制定完整的开发计划。每个功能点都包含：当前状态、目标状态、详细交互设计、用户体感描述。

不考虑实现成本，只关注「应该做成什么样」和「用户会感受到什么」。

---

## 一、流式输出与实时交互体验

### 1.1 零延迟首 Token

**当前状态**：管线启动后需等待编排器 LLM 调用（1-3s）才产生第一个 token。对话类请求在意图解析完成后才进入 LLM 流式，非对话请求的分析 token 以整块字符串一次性插入。

**目标**：用户按下发送后 200ms 内看到第一个文字开始出现。

**详细设计**：

- **预连接策略**：在用户输入过程中（检测到键盘活动），后台预先发起 provider 连接，保持 warm TCP / TLS session。当用户按下发送时，第一个 chunk 已经可以立刻返回
- **流式编排器**：将 `runOrchestrator` 从非流式 JSON 调用改为流式调用。编排器的推理过程（reasoning）以逐字流式方式输出，用户看到：
  ```
  正在分析你的请求...
  识别到这是一个复合意图，包含 3 个独立任务：
  → 创建 React 学习计划
  → 将学习任务排入日程
  → 设置每周复盘提醒
  依赖关系：任务 2 和任务 3 需等待任务 1 完成后执行...
  ```
  这段文字不是一次性出现的，而是一个字一个字打出来的

- **流式意图解析**：`resolveAgentIntent` 同样改为流式。对于非对话意图，输出推理过程：
  ```
  判断意图：创建计划（置信度 0.92）
  关键依据：你提到了「学习路线」「阶段」「目标」
  ```

- **骨架屏 + 渐进填充**：气泡中的分析区域先用占位骨架显示结构（灰色块表示即将出现的段落），随着流式 token 到达逐步填充为真实文字。骨架结构根据编排器的 plan 结构提前生成：
  - 第一段骨架：「分析结论」（编排器输出）
  - 第二段骨架：「意图识别」（意图解析输出）
  - 第三段骨架：「执行计划」（DryRun 输出，仅当有写操作时出现）

- **并行分析 + 赛马机制**：编排器和意图解析不是严格串行的。意图解析可以在编排器的 reasoning 还在流式输出时就启动（因为只需要 message + history，不需要等编排器完成）。当编排器判断为 compound 时，已经跑完的意图解析结果作为 preResolvedIntent 使用；当编排器判断为 single 时，两个结果互相校验

**用户体感**：
- 按下发送 → 立刻看到「正在分析...」→ 编排器推理逐字出现 → 意图判断同时出现 → 如果涉及写操作，执行计划紧跟着出现 → 最终回复逐字流式输出
- 整个过程没有「等待空白 → 文字一闪」的断层，而是连续的、渐进的信息流

### 1.2 分层流式输出

**当前状态**：所有 token 都在同一个气泡中，分析过程和最终回复混在一起。

**目标**：气泡中出现视觉分层，区分「思考过程」和「最终回复」。

**详细设计**：

- **思考块（Thinking Block）**：气泡内部的折叠区域，默认展开但视觉上与回复区分
  - 浅色背景、左边框带颜色标记
  - 标题栏：「Agent 正在思考...」→ 流式更新为「分析完成」
  - 内容区包含编排器推理、意图判断、计划拆解等
  - 可手动折叠/展开
  - 思考块内的文字也是逐字流式出现的

- **回复块（Response Block）**：思考块下方的正常文字区域
  - 标准的白色背景，与普通消息一致
  - 如果思考块存在，回复块与思考块之间有一条细分割线
  - 分割线在思考块完成后、回复块开始前出现

- **流式状态指示器进化**：
  - 当前：底部一个闪烁光标
  - 目标：思考阶段显示脉冲动画的脑图标 + 当前步骤名称（「正在分析意图...」「正在拆解计划...」）
  - 回复阶段切换为打字光标
  - 完成阶段显示绿色对勾 + 耗时（「3.2s」）

- **步骤时间戳**：思考块内每个分析步骤旁显示相对时间戳
  ```
  ⏱ 0.0s  ·  正在分析你的请求...
  ⏱ 0.3s  ·  已加载 3 个计划、2 份清单
  ⏱ 1.2s  ·  编排器判断为单一意图
  ⏱ 2.1s  ·  识别意图：创建学习计划
  ```

**用户体感**：气泡不再是一面纯文字墙，而是有结构、有时间感的信息流。用户可以快速浏览思考过程（知道 Agent 为什么做出这个决定），也可以折叠它只看结果。

### 1.3 可中断 + 可修正的对话流

**当前状态**：只能通过 `stopGeneration` 完全停止。停止后无法继续、无法修正参数。

**目标**：支持三种中断模式 + 中断后继续对话。

**详细设计**：

- **软中断（Pause / 「等一下」）**：
  - 用户点击暂停按钮或按 Esc
  - Agent 停止当前 token 流式，但保留已接收的上下文
  - 气泡中显示「已暂停」，出现两个按钮：「继续」/「修改」
  - 点击「继续」→ 从暂停点继续流式
  - 点击「修改」→ 出现输入框，用户可以补充/修正：「先改成每天 2 小时」
  - Agent 根据新输入调整后续输出，之前已流式的 token 保留

- **硬中断（Stop / 「取消」）**：
  - 完全停止当前请求，AbortController 取消 fetch + provider 请求
  - 气泡中保留已输出的内容，标记为「已取消」
  - 用户可以立即发送新消息，Agent 理解上下文是被取消的操作
  - 后台清理：如果有已执行的部分写操作，触发局部回滚

- **分支中断（Fork / 「换个方向」）**：
  - 用户选中气泡中的某段文字，右键出现「从这里重新来」
  - Agent 保留选中位置之前的所有内容，从该点重新生成
  - 如果之前是写操作，回滚已执行部分后重新执行

- **中断后的上下文保持**：
  - 中断点之前的 token、trace steps、分析结果全部保留在 working memory
  - 下一次 sendMessage 时，`pendingAction` 会被调整为中断状态
  - Agent 知道「上次用户在 X 步骤时中断了，原因是 Y」

**用户体感**：对话不再是「要么等完、要么全丢」的二选一。可以随时介入、修正方向、或部分回退。

---

### 1.4 渐进式结果预览

**当前状态**：DryRun 完成后一次性展示 `ProposedAction` 确认卡片。

**目标**：在执行计划生成过程中，实时在 Inspector 面板中渲染即将发生的变化。

**详细设计**：

- **Inspector 实时更新**：当编排器确定意图后，Inspector 面板的「Changes」标签就开始渲染
  - 先显示骨架占位（标题行 + 3 个变更卡片骨架）
  - DryRun 每验证一个操作，对应的骨架卡片就填充为真实内容
  - 卡片包含：操作类型图标、影响文档名称、before/after 对比
  - 如果 DryRun 发现冲突（如日程冲突），该卡片变为警告色（黄色/红色边框）

- **Before/After 对比视图**：
  - 左右双栏布局，左栏「当前状态」，右栏「变更后」
  - 变更字段用高亮色标记（绿色=新增、黄色=修改、红色=删除）
  - 对于计划拆解：左栏是空的阶段列表，右栏逐渐填充阶段名称和预计天数

- **风险指示器**：确认按钮旁有风险等级指示
  - 低风险（仅查询）：绿色，无需确认
  - 中风险（创建/修改单个文档）：黄色，「确认」按钮
  - 高风险（批量操作/删除/公开时间线）：红色，「仔细检查后确认」按钮，需额外点击一次
  - 每个风险等级旁标注影响范围（「将修改 1 个计划、2 个清单」）

**用户体感**：不是「等 Agent 想好了然后扔给你一个确认弹窗」，而是「看着 Agent 一步步检查和构建变更，你可以在任何时候介入」。

## 二、Agent 自主性与反馈循环

### 2.1 执行-观察-决策循环（Read-Eval-Print Loop）

**当前状态**：管线一次性规划所有任务 → 批量执行 → 返回结果。没有中间观察和动态调整。

**目标**：实现真正的 Agentic Loop，每步执行后根据结果决定下一步。

**详细设计**：

- **Loop 核心架构**：
  ```
  while (taskQueue.length > 0 && turns < maxTurns) {
    const task = taskQueue.shift();
    const result = await executeTask(task);

    // 观察结果
    const observation = buildObservation(result);

    // 决策下一步
    const decision = await llm.decideNextAction({
      originalGoal: userMessage,
      completedTasks: completedTasks,
      currentResult: observation,
      remainingTasks: taskQueue,
      errors: recentErrors,
    });

    switch (decision.action) {
      case "continue":
        // 按原计划继续
        break;
      case "replan":
        // 根据新信息重新规划剩余任务
        taskQueue = decision.newTasks;
        break;
      case "ask_user":
        // 需要用户澄清/确认
        return { type: "clarification", question: decision.question };
      case "abort":
        // 目标已达成或无法继续
        return { type: "complete", summary: decision.summary };
      case "retry":
        // 重试当前任务
        taskQueue.unshift(task);
        break;
    }
  }
  ```

- **观察构建器（buildObservation）**：
  - 将工具执行的返回结果转化为 LLM 可理解的自然语言描述
  - 包含：操作类型、影响文档、成功/失败状态、关键数据变化
  - 对于查询操作：展示查询结果的关键数据点（如「当前有 3 个活跃计划，其中"React 学习"进度为 40%」）
  - 对于写操作：展示写入前后的数值对比
  - 对于失败操作：展示错误类型和建议（「日程冲突：5 月 22 日 14:00-16:00 已有『团队周会』」）

- **maxTurns 与终止条件**：
  - 默认 maxTurns = 10（单次对话最多执行 10 个工具调用）
  - 达到 maxTurns 时，总结已完成和未完成的任务，询问用户是否继续
  - 提前终止条件：目标已达成、用户明确拒绝、连续 3 次同类型失败、检测到循环

- **每轮的状态更新**：
  - 气泡中实时更新「已完成 X/Y 个任务」
  - Inspector 面板实时刷新受影响文档的最新状态
  - Trace timeline 显示每个 turn 的执行链路

**用户体感**：Agent 不再是一次性规划然后批量执行的「静态管道」，而是会「边做边看边调整」的动态助手。遇到问题会自动重试或调整策略，只在真正需要时才打扰用户。

### 2.2 动态重规划

**当前状态**：`replan.ts` 存在但未集成到主管线。

**目标**：执行过程中遇到失败或新信息时，自动调整剩余计划。

**详细设计**：

- **触发条件**：
  - 工具执行失败（数据库写入失败、冲突检测触发）
  - DryRun 发现与预期不符（如「计划名已存在，请换一个名字」）
  - 执行结果揭示新信息（如「查询发现该计划已经有 5 个未完成任务，建议先处理这些」）
  - 用户在中途插入新要求

- **重规划策略**：
  - **局部重规划**：仅调整当前失败的任务。例如日程冲突 → 自动建议下一个可用时段
  - **依赖重规划**：当前任务的后续依赖任务也需调整。例如创建计划失败 → 后续的「排入日程」和「设置复盘」也需要重新规划
  - **全局重规划**：重新调用编排器，根据所有已完成任务和最新状态重新生成完整计划

- **重规划透明度**：
  - 气泡中显示重规划通知：「检测到日程冲突，正在重新安排...」
  - 重规划结果以 diff 形式展示：旧计划 vs 新计划的对比
  - 用户可以接受新计划或要求再次调整

- **重规划预算**：每次对话最多触发 3 次全局重规划，防止无限重规划循环

**用户体感**：Agent 不会在遇到第一个障碍时就放弃或返回一个模糊的错误。它会自己尝试绕过去，并告诉你它做了什么调整。

### 2.3 多轮自主执行

**当前状态**：每次写操作都需要用户确认。

**目标**：支持可配置的自主执行级别，低风险操作自动执行。

**详细设计**：

- **自主执行级别**：
  - **Level 0 - 完全确认**：每个写操作都需要确认（当前模式，适合新用户）
  - **Level 1 - 低风险自动**：仅查询和低风险操作（如取消日程）自动执行，中高风险需确认
  - **Level 2 - 同领域自动**：同一计划/清单内的连续操作，仅第一次需确认，后续自动
  - **Level 3 - 全部自动**：所有操作自动执行，仅在完成后展示摘要（适合高度信任的用户）

- **级别记忆**：用户对特定类型的操作的选择会被记住
  - 「总是自动执行日程调整」
  - 「创建计划前总是问我」
  - 这些偏好保存在 AgentMemory 中，type = `confirmation_preference`

- **批量自动执行摘要**：Level 2/3 下，多个自动执行的操作完成后，气泡中展示摘要：
  ```
  已自动完成 3 项操作：
  ✓ 创建学习计划「React 入门」
  ✓ 添加日程「React 学习」5/22 - 6/22 每天 14:00-16:00
  ✓ 设置每周五 17:00 复盘提醒
  ```

- **撤销窗口**：自动执行的操作在 30 秒内可以通过「撤销」按钮或 `Ctrl+Z` 回滚

**用户体感**：熟练用户不再被频繁的确认弹窗打断。Agent 像真正的助手一样，知道什么时候该自己动手、什么时候该问一下。

### 2.4 子任务并行 + 依赖编排

**当前状态**：编排器按层并行（无依赖的任务放在同一层用 Promise.all），但同 checklist 的操作被强制串行。

**目标**：更智能的并行策略 + 可视化的任务依赖图。

**详细设计**：

- **依赖图可视化**：在 Inspector 面板的「Timeline」标签中渲染任务依赖图
  - 节点 = 每个子任务（显示图标 + 标签）
  - 边 = 依赖关系（箭头从上游指向下游）
  - 节点颜色：pending（灰）→ running（蓝+脉冲）→ done（绿）→ failed（红）
  - 并行层用虚线框分组
  - 实时更新：随着执行推进，节点颜色逐步变化

- **智能冲突检测**：
  - 编译时冲突：同一文档的写操作不能在并行层中（当前已实现）
  - 语义冲突：两个操作虽操作不同文档但语义相关（如「删除计划 A」和「将任务从计划 A 迁移到计划 B」），应该串行且有序
  - 资源冲突：两个操作都需要同一个 LLM 调用，可以共享结果

- **动态并行度调整**：
  - 根据操作类型和系统负载自动调整并行度
  - LLM 调用类操作最多 2 个并行（受 API rate limit 约束）
  - 数据库读写类操作最多 5 个并行
  - 用户可查看当前并行度并在设置中调整上限

**用户体感**：复杂操作不再是依次执行然后汇总，而是可以看到一张实时更新的任务图，知道哪些已经完成、哪些正在进行、哪些还在等待依赖。

## 三、工具生态

### 3.1 文件系统工具集

**当前状态**：无任何文件系统操作能力。

**目标**：Agent 可以读写用户的本地文件，成为真正的「个人工作台助手」。

**详细设计**：

- **文件读取工具**：
  - `read_file(path, startLine?, endLine?)` → 读取文件内容，支持行号范围
  - `list_directory(path, recursive?, pattern?)` → 列出目录内容，支持 glob 模式
  - `search_files(pattern, path?)` → 在项目中搜索匹配 pattern 的文件名
  - `grep_files(query, path?, includePattern?, excludePattern?)` → 在文件内容中搜索关键词/正则

- **文件写入工具**：
  - `write_file(path, content)` → 写入文件（创建或覆盖）
  - `edit_file(path, oldString, newString)` → 精确字符串替换
  - `create_directory(path)` → 创建目录
  - `delete_file(path)` / `delete_directory(path, recursive?)` → 删除文件/目录

- **安全边界**：
  - 默认工作目录为项目根目录，不可访问系统目录（/etc, /System, C:\Windows 等）
  - 可配置白名单路径（如 ~/Documents, ~/Projects）
  - 可配置黑名单路径（如 .env, *.secret, node_modules）
  - 删除操作始终需要确认
  - 所有文件操作记录到 AgentRun 审计日志

- **与现有功能的联动**：
  - `save_memory` 工具可导出记忆到本地 Markdown 文件
  - `weekly_review` 生成的周报可保存为 Markdown
  - 计划/清单可导出为 JSON/YAML 备份

**用户体感**：Agent 可以帮你整理项目文件、搜索代码片段、批量重命名、生成配置文件。它不只是「知道你的计划」，还能「管理你的文件」。

---

### 3.2 Shell / 命令执行工具

**当前状态**：无命令执行能力。

**目标**：Agent 可以执行安全的系统命令。

**详细设计**：

- **命令执行工具**：
  - `run_command(command, cwd?, timeout?)` → 执行 shell 命令，返回 stdout/stderr/exit code
  - `run_script(scriptPath, args?)` → 执行脚本文件
  - 默认超时 120 秒，可配置

- **安全策略**：
  - 默认禁用，需用户在设置中显式开启
  - 白名单命令模式：只允许预定义的命令/脚本列表
  - 禁止模式：`rm -rf /`, `sudo`, `chmod 777`, 管道到危险命令
  - 工作目录限制：命令只能在项目目录和用户 home 目录下执行
  - 环境变量过滤：不暴露敏感环境变量（SECRET, KEY, TOKEN, PASSWORD）
  - 每次执行前展示完整命令，高风险命令（包含 rm, delete, drop, format）需二次确认

- **使用场景**：
  - 运行项目测试：`npm test -- --coverage`
  - 安装依赖：`npm install react-hook-form`
  - 查看 git 状态：`git status && git diff --stat`
  - 运行 lint：`npx eslint src/ --fix`
  - 启动开发服务器：`npm run dev`
  - 数据处理脚本：`python scripts/analyze_logs.py`

**用户体感**：Agent 不只是聊计划和清单，还能帮你跑测试、装依赖、看 git 状态。从「效率笔记工具」进化为「开发工作台」。

### 3.3 网络访问与搜索工具

**当前状态**：无网络访问能力。

**目标**：Agent 可以搜索网页、抓取内容、调用外部 API。

**详细设计**：

- **网页搜索**：`search_web(query, maxResults?)` → 返回搜索结果列表（标题 + URL + 摘要）
- **网页抓取**：`fetch_url(url, extractMode?)` → 抓取网页内容并转为 Markdown
  - extractMode: "full"（全部内容）/ "article"（仅正文）/ "metadata"（仅元数据）
- **API 调用**：`call_api(url, method, headers?, body?, authType?)` → 调用外部 API
  - authType: "none" / "bearer" / "basic" / "api_key"
  - API key 从 AgentSettings 的安全存储中读取，不在对话中明文显示

- **使用场景**：
  - 「最近 React 19 有什么新特性？」→ 搜索 + 抓取官方文档
  - 「帮我查一下这个 GitHub issue 的讨论」→ 抓取 issue 页面
  - 「把这个网页的内容总结一下」→ 抓取 + 摘要
  - 「检查我的 API 是否在线」→ 调用健康检查端点

- **内容缓存**：抓取的内容缓存 15 分钟，相同 URL 不重复抓取

**用户体感**：Agent 的知识不再局限于训练数据和本地上下文，可以实时获取最新信息。

### 3.4 Git 集成工具

**当前状态**：无 Git 操作能力。

**目标**：Agent 可以执行常见的 Git 操作。

**详细设计**：

- **Git 工具集**：

  - `git_diff(staged?, path?)` → 查看变更
  - `git_log(count?, author?)` → 提交历史
  - `git_branch(list?, create?, delete?, switch?)` → 分支管理
  - `git_add(files)` → 暂存文件
  - `git_commit(message)` → 创建提交
  - `git_push(branch?)` / `git_pull(branch?)` → 推拉远程

- **安全策略**：
  - 强制推送（--force）和重置（reset --hard）始终需要用户确认
  - 提交信息由 Agent 生成但用户可编辑
  - 推送前展示将要推送的提交列表

- **智能提交信息**：根据 diff 内容自动生成规范的 commit message
  - 遵循项目现有的 commit 风格（从 git log 学习）
  - 格式：`type(scope): description`
  - 用户可在确认前编辑

**用户体感**：日常的 git add/commit/push 流程可以一句话完成：「把这轮改动提交并推送」。

## 四、记忆与个性化

### 4.1 分层记忆架构

**当前状态**：AgentMemory 是扁平的 4 类标签（偏好/事实/规则/风格），无层次结构。

**目标**：四层记忆体系，从核心身份到临时任务上下文。

**详细设计**：

- **L1 — 身份记忆（Identity）**：关于用户本人的核心信息，永不衰减
  - 姓名、角色、职业
  - 核心工作领域（如「前端工程师」「在读研究生」）
  - 长期目标（如「6 个月内转行到 AI 领域」）
  - 沟通偏好（如「用中文回复，技术术语保留英文」）
  - 来源：初始配置 + 手动录入，极少自动更新

- **L2 — 项目记忆（Project）**：用户正在推进的各项事务，随项目生命周期变化
  - 每个活跃计划/项目一个记忆条目
  - 包含：目标、关键里程碑、当前状态、相关资源路径
  - 当计划完成或归档时，对应记忆标记为 archived
  - 自动从计划/清单/日程中抽取摘要更新

- **L3 — 经验记忆（Experience）**：从交互中学到的经验，有衰减机制
  - 用户的反馈模式：「上次你说 X 方案更好，以后类似情况用 X」
  - 成功的操作模式：「这种计划结构以前效果很好」
  - 失败的教训：「上次这样排期导致冲突，以后注意检查」
  - 衰减：90 天未引用的经验记忆置信度减半，180 天归档
  - 矛盾解决：新经验与旧经验冲突时，置信度高的保留，或询问用户

- **L4 — 会话记忆（Session）**：当前对话的临时上下文
  - 本次对话中讨论的所有话题和决策
  - 用户当前的情绪/紧迫感（从语言中推断）
  - 对话结束（或长对话的段落后）自动压缩为摘要存入 L3

**用户体感**：Agent 越用越懂你。不仅仅是记住你的偏好，还会累积经验、关联项目、理解你的长期目标。

---

### 4.2 自动记忆提取与巩固

**当前状态**：`autoArchiveMemoryFromExecution` 仅从用户消息中提取工作流偏好关键词。

**目标**：每次对话结束后自动提取有价值的记忆，经用户确认后存入。

**详细设计**：

- **对话后记忆提取流程**：
  1. 对话结束（用户明确结束或长时间无交互）
  2. 后台异步调用 LLM 分析整个对话
  3. 提取三类信息：
     - **新事实**：用户提到的新信息（如「我下周开始学 Rust」）
     - **偏好变化**：用户表达的新偏好（如「以后用更简洁的风格」）
     - **经验教训**：用户表达的满意/不满（如「这个计划太密集了，调整一下」→ 学到的教训是「该用户的计划偏好宽松节奏」）
  4. 生成 1-3 条候选记忆，以通知/卡片形式展示给用户
  5. 用户可选择：保存 / 编辑后保存 / 忽略

- **记忆去重与合并**：
  - 新提取的记忆与已有记忆做向量相似度比较
  - 相似度 > 0.85 → 合并（更新已有记忆，记录版本历史）
  - 相似度 0.5-0.85 → 标记为可能相关，征求用户意见
  - 相似度 < 0.5 → 作为全新记忆

- **记忆置信度**：每记忆条目有 confidence 字段
  - 用户手动保存：confidence = 1.0
  - 自动提取且用户确认：confidence = 0.9
  - 自动提取且用户未反驳：confidence = 0.7
  - 自动提取但用户曾表达矛盾信息：confidence = 0.4

**用户体感**：每次对话结束后，Agent 会主动说「我从这次对话中学到了几件事，要帮你记住吗？」用户不用手动整理，记忆自然积累。

### 4.3 反馈学习循环

**当前状态**：无反馈机制。用户的纠正/不满不会被系统学习。

**目标**：用户每次纠正都能被转化经验，避免重复犯错。

**详细设计**：

- **隐式反馈检测**：在对话中自动检测用户的反馈信号
  - 正面信号：「好的」「不错」「就这样」「比上次好」
  - 负面信号：「不对」「不是这个意思」「重新来」「太啰嗦了」「太简略了」
  - 修正信号：「改成...」「应该是...」「换个方式...」
  - 行为信号：用户点击「撤销」按钮、手动修改 Agent 的输出

- **反馈记录结构**：
  ```yaml
  feedback_type: "correction" | "confirmation" | "dissatisfaction" | "praise"
  context: "用户说"不对，不是创建新计划，是更新现有的""
  original_action: "Agent 准备创建新计划"
  corrected_action: "Agent 改为查询并更新已有计划"
  learned_rule: "当用户说'我的XX计划'时，优先查询已有计划而非创建新的"
  confidence: 0.85
  ```

- **反馈应用**：
  - 实时应用：当前对话中立即调整后续行为
  - 跨会话应用：已确认的反馈规则存储到 L3 经验记忆
  - 相似场景匹配：下次遇到类似请求时，检索相关 feedback 并调整行为
  - 冲突处理：多条 feedback 矛盾时，优先采纳最近的、置信度高的

- **用户反馈面板**：在每次回复后提供快捷反馈按钮
  - 👍 有帮助 / 👎 不准确 / 🔄 换个方式
  - 点击 👎 时弹出简要选择：「哪里不对？」→ 意图理解错误 / 执行结果不对 / 风格不合适 / 其他

**用户体感**：Agent 不会犯同样的错误两次。你纠正一次，它就记住一次。反馈越用越精准。

### 4.4 跨会话上下文保持

**当前状态**：会话之间通过 `AgentThread` 持久化消息，但每次新对话需手动加载 thread。

**目标**：打开应用时自动恢复到上次的工作上下文。

**详细设计**：

- **会话恢复**：
  - 打开 Dashboard → 自动加载最近的活跃 thread
  - 展示「自上次对话以来的变化摘要」（如在用户离线期间，Agent 检测到的日程冲突、计划过期等）
  - 快速导航：侧边栏展示最近 5 个 thread 的标题 + 最后活跃时间

- **上下文预加载**：
  - 应用启动时，后台预加载可能需要的上下文（活跃计划、本周日程、最近记忆）
  - 减少首次对话的延迟
  - 上下文新鲜度标记：如果上次加载的上下文已过 30 分钟，自动静默刷新

- **跨设备同步**：未来支持多设备使用时的记忆和会话同步（通过 Payload CMS 的云端存储）

**用户体感**：打开应用就像从未离开过。Agent 主动告诉你「你不在的时候，XX 计划的截止日期快到了」。

## 五、上下文窗口管理

### 5.1 智能上下文压缩

**当前状态**：聊天历史硬截断为 12 条消息，无压缩/摘要机制。

**目标**：保持无限对话能力，通过智能压缩确保上下文不丢失。

**详细设计**：

- **分层压缩策略**：
  - **近期消息（最近 8 条）**：完整保留，一字不改
  - **中期消息（9-20 条）**：压缩为摘要，保留关键决策和转折点
  - **远期消息（20 条以上）**：高度压缩为要点列表，仅保留改变系统状态的操作和重要用户反馈

- **压缩触发时机**：
  - 消息数超过 20 条时触发首次压缩
  - 之后每新增 10 条消息触发一次增量压缩
  - 压缩异步后台执行，不阻塞用户交互

- **压缩算法**：
  - 调用 LLM 进行摘要：输入完整的近期 + 中期消息，输出结构化摘要
  - 摘要包含：
    - 对话目标（用户想达成什么）
    - 已完成的操作（改变了什么数据）
    - 未完成的待办（还有什么没做）
    - 用户表达的关键偏好和反馈
    - 重要的上下文线索（日期、名称、数字）
  - 摘要以 Markdown 格式存储在 thread 的 metadata 中

- **压缩后恢复**：当用户引用被压缩的内容时（如「上次那个计划...」），Agent 可以：
  - 从摘要中找到线索并响应
  - 如果摘要信息不足，加载原始的 thread messages 进行精确检索
  - 告知用户「这是根据我们之前对话的摘要回忆的，如果需要更精确的信息，我可以加载完整对话记录」

**用户体感**：可以无限聊下去，Agent 不会「忘记」之前说的内容。长对话体验和短对话一样好。

---

### 5.2 动态上下文预算管理

**当前状态**：`DEFAULT_AGENT_CONTEXT_BUDGET` 是固定值，所有内容类型共享同一预算。

**目标**：根据当前任务类型动态分配上下文预算，重要的内容给更多空间。

**详细设计**：

- **预算分配策略**：
  - 总预算：根据模型 context window 的 70%（留 30% 给回复和 system prompt）
  - 分配权重：
    - 对话历史：30%（其中近期消息占 20%，摘要占 10%）
    - 工作区上下文（计划/清单/日程）：30%
    - 长期记忆：15%
    - 工具执行结果：15%
    - 系统 prompt 和指令：10%

- **动态调整**：
  - 如果当前意图是「查询进度」→ 增加工作区上下文预算到 45%，减少工具执行结果到 5%
  - 如果当前意图是「创建计划」→ 增加对话历史到 35%（需要理解用户完整意图），减少记忆到 10%
  - 如果对话中涉及很多工具调用 → 增加工具执行结果预算，减少历史消息到 20%

- **预算可视化**：在 Inspector 面板的「Context」标签中展示
  - 彩色条形图展示各部分实际占用的 token 数
  - 用颜色标记：绿色（正常）/ 黄色（接近上限）/ 红色（已压缩）
  - 点击每部分可展开查看具体内容

**用户体感**：Agent 会自动判断当前最需要什么信息，把有限的上下文窗口用在刀刃上。

---

### 5.3 Prompt 缓存利用

**当前状态**：每次请求重新构建完整 prompt，无缓存机制。

**目标**：利用 LLM provider 的 prompt caching 功能，降低延迟和成本。

**详细设计**：

- **缓存分层**：
  - Tier 1（静态，热缓存）：System prompt 和工具定义，变动极少
  - Tier 2（半静态，温缓存）：长期记忆和工作区上下文摘要，每 5 分钟或检测到变化时刷新
  - Tier 3（动态，不缓存）：用户最新消息、对话历史近 8 条、实时工具结果

- **缓存失效策略**：
  - 检测到计划/清单/日程的增删改 → 失效 Tier 2 缓存
  - 检测到长期记忆更新 → 失效 Tier 2 中记忆部分
  - 切换到新的 AgentThread → 失效 Tier 2 中对话相关部分

- **缓存命中可视化**：在 token 用量指示器中展示缓存节省
  - 「本次请求：1,200 tokens（缓存命中 8,500 tokens）」

**用户体感**：越常用的对话场景越快。高频操作（如「今天有什么日程」）几乎秒回。

## 六、安全与可靠性

### 6.1 事务性执行与自动回滚

**当前状态**：复合计划中多个写操作无事务保证，部分回滚策略占位未实现。

**目标**：多步骤写操作为一个原子单元，任意步骤失败则全部回滚。

**详细设计**：

- **事务管理器**：
  - 执行前为每个复合计划创建一个事务上下文
  - 每步写操作执行前，先记录 before-snapshot
  - 如果所有步骤成功 → 提交事务，清除 snapshot
  - 如果任一步骤失败 → 自动回滚所有已执行步骤，恢复到 before-snapshot 状态

- **Snapshot 机制**：
  - 对所有 Payload CMS collection 的修改操作，在写入前自动创建 deep-clone snapshot
  - snapshot 存储在内存中（同一次请求内），不持久化
  - 回滚时按执行顺序倒序恢复

- **补偿事务**：对于无法简单回滚的操作（如已发送的通知、已触发的 webhook），执行补偿操作
  - 例如：发送了日程确认通知 → 回滚时发送日程取消通知

- **部分成功处理**：
  - 如果事务中 5 个步骤，4 个成功 1 个失败
  - 选项 A（默认）：自动回滚全部 4 个成功步骤，返回错误
  - 选项 B（用户可选）：保留已成功的步骤，仅报告失败的步骤，让用户决定

**用户体感**：再也不会出现「创建了计划但日程没排上，两边数据不一致」的情况。要么全成功，要么全回滚。

---

### 6.2 分级权限系统

**当前状态**：所有写操作的确认流程相同（确认/取消）。

**目标**：细粒度权限控制，用户可配置不同操作的审批级别。

**详细设计**：

- **权限级别定义**：
  - **auto**：自动执行，不询问（仅查询操作）
  - **notify**：自动执行，完成后通知用户
  - **confirm_once**：每次会话中首次执行时确认，后续自动
  - **confirm_always**：每次执行都需确认
  - **forbid**：禁止执行

- **权限分组**：
  | 操作组 | 默认级别 | 包含工具 |
  |---|---|---|
  | 查询 | auto | 所有 query_* 工具 |
  | 计划修改 | confirm_once | compose_plan, create_plan, append_plan_item |
  | 清单修改 | confirm_once | complete_plan_item, add_completion_note |
  | 日程修改 | confirm_always | compose_schedule_item, reschedule_item, cancel_schedule_item |
  | 时间线 | confirm_always | compose_timeline_event |
  | 记忆 | confirm_once | save_memory |
  | 文件读取 | auto | 所有文件读取 |
  | 文件写入 | confirm_always | 所有文件写入 |
  | 命令执行 | confirm_always | 所有命令 |
  | 网络访问 | confirm_once | 所有网络操作 |

- **权限配置 UI**：
  - Settings 面板中展示所有权限组
  - 每行：操作组名称 + 描述 + 下拉选择权限级别
  - 顶部有快速预设：新手（全部 confirm_always）/ 标准（上表默认）/ 专家（大量 auto）
  - 权限变更立即生效，不需重启

- **权限临时提升**：在某次对话中，用户可以临时提升/降低某个操作组的权限级别，仅本次对话有效

**用户体感**：不再被统一的确认弹窗困扰。风险高的操作多问一句，风险低的自动处理。你的使用习惯决定了确认频率。

### 6.3 降级与容错

**当前状态**：LLM provider 不可用时回退到启发式解析，但工具执行失败无重试。

**目标**：多层降级策略，确保核心功能在任何情况下都可用。

**详细设计**：

- **LLM Provider 降级链**：
  - 主 Provider（如 GLM）→ 备用 Provider 1（如 OpenAI）→ 备用 Provider 2（如 Z.ai）→ 本地启发式
  - 切换条件：连续 3 次失败、超时 10s 以上、返回 5xx
  - 切换后自动在该 Provider 上重试当前请求
  - 降级时在 UI 中显示通知：「主模型暂时不可用，已切换到 OpenAI」

- **工具执行重试策略**：
  - **瞬时错误**（网络超时、数据库锁）：立即重试，最多 3 次，指数退避（1s/2s/4s）
  - **业务错误**（冲突检测、验证失败）：不重试，展示具体原因和建议
  - **未知错误**：重试 1 次，仍失败则终止当前操作并报告

- **功能降级模式**：
  - 当 Agent 核心依赖（Payload CMS）不可用时：
    - 仍可进行对话（LLM 不依赖 Payload）
    - 写操作排队，待恢复后批量执行
    - UI 中显示离线状态条：「数据库连接异常，写操作已排队等候恢复」
  - 当 LLM 完全不可用（所有 provider 失败）时：
    - 降级为纯启发式模式
    - 支持的意图：查询进度、取消/确认待处理操作、简单的关键词匹配
    - UI 中显示：「AI 模型暂时不可用，仅支持基础命令操作」

- **健康检查**：
  - 每分钟检查所有 Provider 和 Payload CMS 的连接状态
  - 状态面板中展示各服务状态指示器（绿色/黄色/红色）

**用户体感**：即使某些服务出问题，Agent 也不会完全瘫痪。它会自动切换到备用方案，并清楚地告诉你当前的能力范围。

### 6.4 审计与合规

**当前状态**：AgentRun 记录基本的执行信息，但无完整的变更历史。

**目标**：所有 Agent 操作的完整审计追踪，可追溯、可复盘。

**详细设计**：

- **审计日志字段**：
  - 时间戳（精确到毫秒）
  - 操作类型（工具名称 + 意图类型）
  - 操作参数（序列化为 JSON）
  - 执行结果（成功/失败/部分成功）
  - 影响文档（collection + document ID + 变更字段）
  - Before/After snapshot（完整的文档前后状态）
  - 用户确认状态（自动/确认/取消）
  - 耗时（ms）
  - Provider 信息（使用的模型、token 消耗、成本估算）
  - 回滚信息（如果触发回滚）

- **审计查询**：
  - Dashboard 中「审计日志」面板
  - 按时间范围、操作类型、影响文档、用户筛选
  - 每条日志可展开查看完整的 before/after diff
  - 支持导出为 JSON/CSV

- **变更回溯**：从审计日志中可以重建任意时间点的系统状态
  - 选择时间点 → 展示该时刻所有文档的状态
  - 用于复盘「为什么这个计划被改成了这样」

**用户体感**：Agent 的所有操作都有据可查。随时可以回顾「Agent 在什么时候改了什么、为什么」。

## 七、UI 与工作台

### 7.1 富文本回复渲染

**当前状态**：Agent 回复为纯文本，无任何格式化。

**目标**：支持 Markdown 渲染、代码高亮、结构化卡片。

**详细设计**：

- **Markdown 渲染**：
  - 标题（h1-h6）
  - 加粗、斜体、删除线

  - 行号显示（可切换）

**用户体感**：Agent 的回复从纯文本升级为富媒体。结构化信息一目了然，代码片段可以直接复制使用。

### 7.2 中间产物实时面板

**当前状态**：Inspector 面板仅在确认阶段展示 ProposedAction。

**目标**：Inspector 面板在管线执行的每个阶段都实时更新对应内容。

**详细设计**：

- **多 Tab 结构**：
  - **Context**：当前加载的上下文信息（计划、清单、记忆、时间线），实时刷新
  - **Timeline**：任务依赖图 + 执行时间线（当前实现，增强为实时更新）
  - **Changes**：DryRun 生成的变更预览（当前实现，增强为渐进填充）
  - **Artifacts**：执行完成后的产物（当前实现）
  - **Memory**：本次对话中引用的记忆 + 新提取的记忆候选

- **Context Tab 详细设计**：
  - 每个上下文类型一个折叠区域（计划/清单/日程/记忆/内容）
  - 每行显示：名称 + 元数据（如计划的进度百分比、日程的时间）
  - 鼠标悬停显示完整摘要
  - 点击跳转到 Payload Admin 对应文档的编辑页
  - 右上角 Pin/Exclude 按钮（当前功能，增强交互）

- **Timeline Tab 详细设计**：
  - 顶部：整体进度条（已完成/进行中/等待中/失败）
  - 主体：依赖图可视化（2.4 节详述）
  - 底部：事件日志（按时间倒序展示每个 step 的状态变化）
  - 每条日志：时间戳 + 图标（运行中=旋转/完成=绿色对勾/失败=红色叉）+ 标题 + 可展开详情

- **Changes Tab 详细设计**：
  - 按影响文档分组
  - 每个文档的变更以卡片形式展示：文档名称 + 变更数量
  - 展开卡片看到 before/after 对比
  - 高风险变更（红色边框）+ 警告文字

**用户体感**：Inspector 不再是「确认时才看一眼」的附属面板，而是贯穿整个对话的实时信息中心。

### 7.3 智能模式切换

**当前状态**：workbench mode 需用户手动选择（ask/execute/plan/review/timeline）。

**目标**：Agent 根据用户输入自动判断最佳模式并切换。

**详细设计**：

- **自动模式检测**：
  - 用户输入「帮我看看...」「分析一下...」「现在进度怎么样」→ ask 模式
  - 用户输入「创建...」「安排...」「添加...」「取消...」→ execute 模式
  - 用户输入「制定...计划」「规划...」「帮我设计...」→ plan 模式
  - 用户输入「这周做了什么」「复盘」「总结」→ review 模式
  - 用户输入涉及具体日期/时间/日程 → timeline 模式
  - 检测逻辑：在意图解析阶段同步判断，以 mode 标签形式返回

- **模式切换动画**：
  - Workbench 顶部模式标签切换时有滑动过渡动画
  - 相关的 Inspector Tab 自动激活（plan → Context Tab，execute → Changes Tab，review → Artifacts Tab）

- **手动覆盖**：用户可以随时手动切换到其他模式，Agent 适应新模式
  - 例如：Agent 自动切到 execute 模式，但用户想先看看 review，手动切换到 review → Agent 改为生成周报而非执行操作

- **复合模式**：某些复杂意图可能需要跨模式
  - 例如：「制定考研计划 + 排日程 + 设置复盘」
  - Agent 在 plan 模式下展示计划拆解 → 切换到 timeline 模式展示日程安排 → 切换到 review 模式确认复盘设置
  - 气泡中不同阶段标注对应模式标签

**用户体感**：不用再想「我应该选哪个模式」，Agent 自动切换到最适合当前任务的面板布局。

### 7.4 可定制 Dashboard 布局

**当前状态**：Dashboard 布局固定，左侧对话 + 右侧 Inspector。

**目标**：用户可自由调整面板大小、位置、可见性。

**详细设计**：

- **面板布局系统**：
  - 拖拽调整面板大小（左右分栏比例、上下高度）
  - 面板可拖拽重新排列（如把 Timeline 拖到对话上方）
  - 面板可弹出为独立窗口（适用于多显示器场景）
  - 面板可折叠/展开（点击标题栏或快捷键）
  - 布局自动保存到 localStorage / user preferences

- **预设布局**：
  - 「标准」：左对话 + 右 Inspector（当前布局）
  - 「专注」：全屏对话，隐藏所有面板
  - 「开发」：左对话 + 右分上下（上=Timeline，下=Context）
  - 「复盘」：左对话 + 右分上下（上=Changes diff，下=审计日志）
  - 用户可创建和命名自己的预设

  - 宽屏（>1400px）：标准三栏（对话 + Inspector + 侧边栏）
  - 中屏（900-1400px）：两栏（对话 + Inspector）
  - 窄屏（<900px）：单栏，Inspector 变为底部抽屉

- **快捷键**：
  - `Ctrl+1` ~ `Ctrl+5`：切换到对应布局预设
  - `Ctrl+[` / `Ctrl+]`：切换 Inspector Tab
  - `Ctrl+\``：切换对话/Inspector 焦点
  - `F11`：专注模式

**用户体感**：Dashboard 像 IDE 的面板系统一样灵活。不同场景用不同布局，随手切换。

**详细设计**：

**用户体感**：不再需要在几十个「Thread #N」中翻找。搜索、标签、摘要让对话管理变得轻松。

## 八、可观测性

### 8.1 成本追踪

**当前状态**：tokenUsage 记录了每次请求的 token 消耗，但未计算成本。

**目标**：实时展示每次对话和累计的成本。

**详细设计**：

- **成本计算**：
  - 根据 provider + model + token 数量计算成本
  - 支持多种 provider 的定价表（GLM、OpenAI、Z.ai 等）
  - 输入 token 和输出 token 分开计算（价格不同）
  - 缓存命中的 token 不计费（或按缓存费率计算）

- **成本展示**：
  - 每条回复底部显示本次请求成本（如「$0.0032」）
  - Status bar 显示本次对话累计成本
  - Settings 面板显示本月/总计成本

- **成本预警**：
  - 单次对话超过 $0.10 时显示黄色提示
  - 单日超过 $1.00 时显示红色警告 + 可配置硬上限
  - 每月成本报告（自动生成 + 发送）

**用户体感**：对 Agent 的使用成本了如指掌。不会某天突然发现 API 账单超支。

### 8.2 性能分析

**当前状态**：trace steps 记录了每步状态，但无聚合分析和可视化。

**目标**：完整的性能分析面板。

**详细设计**：

- **延迟分解图**（瀑布图）：
  - 横轴 = 时间（ms），纵轴 = 每个步骤
  - 每步用色块表示实际耗时，不同颜色代表不同类型
  - 展示每步的开始时间、耗时、在总时间中的占比
  - 可折叠查看步骤内的子步骤耗时

- **性能指标**：
  - **TTFR**（Time To First Response）：从请求发送到第一个 token 出现的延迟
  - **TTCR**（Time To Complete Response）：从请求发送到完成回复的总延迟
  - **TTFE**（Time To First Execute）：从请求发送到第一个工具执行完成的延迟
  - **Streaming Ratio**：流式输出时间占总响应时间的比例

- **性能趋势**：
  - 过去 24h/7d/30d 的延迟变化折线图
  - 按 intent 类型分组展示平均延迟
  - 按 provider 分组展示平均延迟
  - 异常检测：自动标记延迟突增的时间点

- **慢请求分析**：
  - 自动标记超过 P95 延迟的请求
  - 展示慢请求的 trace 详情，高亮最慢的步骤
  - 给出优化建议（如「编排器 LLM 调用占了 60% 的时间，考虑缓存或简化 prompt」）

**用户体感**：当感觉「这次怎么这么慢」时，可以立刻看到具体是哪个环节慢了、为什么慢了。

### 8.3 质量监控

**当前状态**：无系统化的质量评估。

**目标**：持续监控 Agent 输出的质量，发现问题趋势。

**详细设计**：

- **质量指标**：
  - **意图准确率**：意图解析结果与用户实际意图的一致率（通过隐式/显式反馈判断）
  - **执行成功率**：工具执行成功/失败/需澄清的比例
  - **用户满意度**：👍 反馈比例
  - **修正率**：用户手动修改或撤销 Agent 输出的比例
  - **一次完成率**：一次对话即完成用户目标的比率（无需后续追问或修正）

- **质量趋势面板**：
  - 各指标随时间变化的折线图
  - 按 intent 类型、provider、workbench mode 分组
  - 当指标恶化超过阈值时自动告警

- **案例库**：
  - 自动收集高满意度案例（👍 + 一次完成）作为 good case
  - 自动收集低满意度案例（👎 + 多次修正）作为 bad case
  - 用于回归测试和 prompt 优化

- **A/B 测试框架**：
  - 支持对 system prompt、工具定义、编排策略进行 A/B 测试
  - 随机分流用户请求到实验组和对照组
  - 按质量指标对比两组表现
  - 统计显著性检验

**用户体感**：不是直接可见的功能，但保障了 Agent 质量持续提升而非退化。
